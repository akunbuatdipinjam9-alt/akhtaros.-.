RECRUITER VIEW / 02

Satu contoh cara gw mikir saat membangun fitur.

Case study singkat ini menunjukkan bukan cuma apa yang dibuat, tetapi juga alasan di balik arsitekturnya.

Filesystem dari desktop shell

01 · Masalah

Renderer browser tidak boleh diberi akses Node.js dan filesystem secara langsung karena itu memperbesar risiko keamanan.

02 · Solusi

Akhtar OS memisahkan main process, preload, dan renderer. API yang dibutuhkan diekspos secara terbatas melalui bridge/IPC.

03 · Hasil

File Manager dan fitur File Access dapat berkomunikasi dengan runtime desktop tanpa menjadikan seluruh renderer punya akses sistem.

04 · Pelajaran

Fitur yang terlihat sederhana ternyata memaksa gw memahami trust boundary, permission, async flow, dan error handling.

renderer  →  preload bridge  →  IPC channel  →  main process
   │              │                 │                 │
   │  user action │  allowlisted    │  validate       │  filesystem
   │  + state     │  API only       │  payload        │  operation
   │              │                 │                 │
   └──────────────┴─────────────────┴─────────────────┴──→ result / error

design goal: minimum privilege, visible failure, predictable state
next step: stronger validation, tests, and signed desktop releases
